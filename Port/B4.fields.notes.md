# Port/B4.fields.notes.md — WinSky Field subsystem → Metal port notes

Companion to `Metal/cell.field.metal` (fieldMapKernel + fieldApplyKernel +
FieldUniforms). Source of truth for the per-field math: `Port/Expanded/
fieldShort.expanded.cpp`. Architectural facts: `Port/CallTree.md` §2 ("Waves
and Fields"). WinSky (`/Users/warren/Dev/WinSky`) was read-only reference,
consulted only where CallTree.md paraphrases rather than quotes the source —
specifically `pixel/Field.cpp` (`Field::calcMap/go/setFxy/setXY/setRT/
calcFade`) and `pixel/FieldFunc.cpp` (`rnd`/`dabs`/`trnc`/`flor`/`wrap`/
`clip`/`pos`/`sgn`/`trwv`/`saw`/`sqwv`) — to resolve the exact blend/wrap
formula, since CallTree.md's own summary ("blend fade[buf[prev][fxyi]] with
the new incoming pixel -> buf[next]") is not literal source. No WinSky file
was modified.

## 1. Map texture format

**Chosen: `rg32Float`, R and G channels hold the exact integer destination-
into-source pixel coordinate `(xPos, yPos)` baked by `fieldMapKernel`,
computed once per selection.**

Semantics: `mapTex.read(gid).xy` = the `(x,y)` texel coordinate in the CELL
texture (same 2048×2048 grid) that `gid` should sample from this frame,
i.e. exactly WinSky's `fxy[gid]` (a resolved flat pixel index) re-expressed
as two coordinates instead of one flat int. No fractional/UV encoding, no
interpolation — the value is written and read as whole-number floats and
consumed via `texture::read()` (nearest, integer-indexed), never `sample()`.

Rejected alternatives and why:
- **`rgba16Float`** — half has only 10 explicit mantissa bits (11 significant
  bits including the implicit leading 1), so integers are exactly
  representable only up to 2048 = 2¹¹. That is *exactly* the cell texture's
  current edge dimension — any future bump to the grid size (or a non-power-
  of-two grid) would silently lose precision at the top end and misalign the
  warp by a texel. `rg32Float` has no such ceiling and costs the same 8
  bytes/pixel as `rgba16Float` (2×32-bit vs 4×16-bit), so there is no size
  penalty for choosing the safer format. (2 unused channels in either case —
  BA of `rgba16Float` would sit idle exactly like the unused packing headroom
  in `rg32Float`; picking `rg32Float` and only declaring 2 channels of intent
  is more honest about what's actually stored.)
- **Storing normalized UV in [0,1) instead of integer texel coords** — would
  require `fieldApplyKernel` to re-multiply by width/height and round every
  frame, defeating the entire compute-once premise. Storing the resolved
  integer coordinate directly means `fieldApplyKernel` does a single
  `uint2(mapTex.read(gid).xy)` and a texture `read()` — no math at all.
- **A flat `int` index (mirroring WinSky's literal `fxy[]`)** — Metal has no
  1-channel 32-bit int texture format usable here without extra unpacking
  logic in the apply kernel for no benefit; two coordinates map directly onto
  `texture::read(uint2)` with zero decode cost.

**Map texture must be allocated at the same width/height as the cell chain
(2048×2048) and reallocated together with it** — `fieldMapKernel` bakes
coordinates in that grid's own index space; a size mismatch between mapTex
and the cell texture silently misaligns every lookup.

## 2. Host regen contract

`fieldMapKernel` is dispatched (full 2048×2048 grid, standard 128×128
threadgroup-of-16×16 dispatch per `Port/Integration.md`) **only** when any of:

1. **`algo` changes** — user selects a different field. Mirrors WinSky
   `if (oldAlgo != algo.v()) calcMap();` (`Field.cpp:325-328`).
2. **A host-exposed `a[]` constant is edited** (see §6 "proposed flo
   leaves") — WinSky has no live-editing UI for `a[]` (they're fixed at
   selection time by the field's own setup code), but since this port hoists
   `a[]` to a host-owned uniform, editing one is functionally equivalent to
   reselecting the same field and must trigger the same regen.
3. **Seed reroll** — an explicit user/host action to redraw the frozen
   per-pixel jitter (algo 0/8/18 only, see §5) and/or reroll the rnd()-seeded
   `a[]` constants (§4) without changing which field is selected. Mirrors
   WinSky's behavior on *reselecting the same field*, which re-runs
   `calcMap()` and therefore redraws `rnd()` — WinSky has no dedicated
   "reroll" gesture, but the underlying mechanism (rerun setup, get fresh
   randoms) is identical.

`fieldMapKernel` must **NOT** run on ordinary frame ticks — that is the
entire point of the two-kernel split (§2.2 of CallTree.md's architectural
fact). `fieldApplyKernel` runs unconditionally every frame, exactly mirroring
`Field::go()`'s per-pixel loop, which has no gate beyond
`passThrough()` (`onoff==0 || algo==FieldNone`) — reproduced here as a
host-side dispatch gate (skip both kernels / pass the cell texture through
unmodified), not encoded in `FieldUniforms`, matching how every other
`cell.rule.*.metal` rule is turned on/off via its flo `on 0/1` leaf rather
than an in-kernel flag (`Port/Integration.md` §"Ping-pong texture
mechanism").

`fadeGain` and `seed` may be updated independently (`fadeGain` every frame is
harmless — it's read fresh by `fieldApplyKernel` regardless — `seed` only
matters at the next `fieldMapKernel` dispatch).

## 3. FieldUniforms byte layout (buffer(0), shared by both kernels)

Total size: **80 bytes**. Swift mirror must match exactly (no automatic
padding assumptions — lay it out explicitly, e.g. a `struct` with the same
field order or a manually packed `[UInt8]`/`simd` type).

| Offset | Size | Type       | Field       | Consumed by       | Meaning |
|---|---|---|---|---|---|
| 0  | 4  | `uint32`  | `algo`      | fieldMapKernel     | Field selector, 0…23 (table in §5). Values ≥24 fall back to case 23 (Lens Flare) via the kernel's `default:` — not a WinSky behavior, a defensive choice for this port. |
| 4  | 4  | `uint32`  | `seed`      | fieldMapKernel     | Per-pixel rnd() seed. Consumed only by algo 0 (Ether Leak), 8 (Star of David), 18 (Smoke in the Mist) — the only 3 of the 24 live fields with a `rnd()` call *inside* the per-pixel body. Bump ONLY on regen (§2), never per frame. |
| 8  | 4  | `float32` | `fadeGain`  | fieldApplyKernel   | WinSky `fader.v()/10000.0` (`Field::calcFade()`, `Field.cpp:265-271`). Linear gain applied to the warped sample before averaging. | 12 | 4  | `float32` | `_pad0`     | —                  | Explicit padding. Keeps `a[]` 16-byte aligned; no functional use. |

## 4. Setup constants (`a[]`) and feedback channel (`d[]`)

### 4.1 Why `a[]` is host-populated, not device-computed

WinSky's `Field::calcMap()` runs **once**, sequentially, on the CPU: it
populates a local `float a[16]` via literal `a[i]=expr;` statements (some
using `rnd()`), then runs the per-pixel `Go*()` loop, which reads that
already-fully-populated `a[]` on every iteration. That "run setup once,
consume many times" structure has no direct GPU equivalent inside a single
massively-parallel kernel — 4M threads cannot cooperatively run a sequential
setup exactly once and share the result without a second dispatch or
CPU-side computation.

This port chooses the most faithful equivalent: **the host (Swift) computes
`a[]` exactly once per regen**, using the same literal formulas as
`fieldShort.expanded.cpp`'s "setup" sections (verbatim arithmetic for
non-random fields; the hash formula below, seeded by `seed`, for
`rnd()`-based fields), and uploads the result into `FieldUniforms.a[]` before
dispatching `fieldMapKernel`. Every GPU thread then reads the same fixed
`a[]`, exactly mirroring WinSky's "setup already resolved before the
per-pixel loop starts" contract — and, as a bonus, this is *more* faithful
than having every thread redundantly re-run `rnd()` itself, since WinSky's
setup genuinely runs once, not once-per-pixel.

**Host-side rnd(range) formula (Swift), for parity with the kernel's
`fieldHashU`/`fieldRndPixel` (same mixing function, different key shape —
setup keys never include `gid`, since a setup constant is one shared value
for the whole field, not a per-pixel one):**

```
key = seed ^ (algo &* 0x9E37_79B9) ^ (aIndex &* 0x27D4_EB2F)
h   = fieldHashU(key)                       // same 32-bit avalanche mix as the .metal file
u01 = Double(h) / 4294967296.0              // [0,1)
rnd(range) = u01 * range
```

`aIndex` = the index being assigned (0-based, in source order for fields
that assign more than one `a[]` slot via `rnd()`).

### 4.3 `d[]` — kernel-local, not a uniform

WinSky's `d[16]` is a **per-pixel** scratch array, assigned fresh inside the
`ForXY` loop body by the `GoD*RT`/`GoD*XY` macro family, read only by
expressions later in the *same* pixel's evaluation — never persisted across
pixels or frames. It is therefore ported as a plain local `float d[16]`
inside `fieldMapKernel`, zero-initialized per invocation, **not** part of
`FieldUniforms`. Of the live 24, only **algo 9 (Strangeitude)** uses it
(`d[0] = sin(theta*a[1])`, 1 of the possible 8 feedback channels the
`GoD8XY` macro supports). No live field needs `d[1..15]`.

## 5. Per-pixel `rnd()` — the 3 fields with genuine spatial jitter

WinSky's `rnd()` is `rand()/RAND_MAX` against a single global libc stream.
Every call anywhere (setup or per-pixel) advances that one stream. Two
different usage patterns exist in the live 24 field bodies, and they produce
visibly different results despite both being "frozen for the field's whole
display duration" (per CallTree.md's central architectural fact — *both*
only run inside `calcMap()`/`fieldMapKernel`, never per rendered frame):

- **Setup `rnd()`** (§4, 9 fields) — one draw, shared by every pixel. Produces
  a single randomized *parameter* (e.g. Disco Ball's segment count), not
  visible per-pixel texture.
- **Per-pixel `rnd()`** (this section, 3 fields) — one draw *per destination
  pixel*, producing a static speckle/grain pattern that holds still for as
  long as the field stays selected. This is what the catalog in
  `Port/CallTree.md` §8 labels "per-pixel jitter" for these three:

| algo | Field | Expression | `fieldRndPixel` slot(s) |
|---|---|---|---|
| 0 | Ether Leak | `theta - sqrt(flor(rnd(1.00999)))` | slot 0 |
| 8 | Star of David | `radius - rnd(0.05)` | slot 0 |
| 18 | Smoke in the Mist | `sin(x) + rnd(0.03) - 0.015` (X), `sin(y)*0.95 + rnd(0.03) - 0.015` (Y) | slot 0 (X), slot 1 (Y) — two independent draws, matching WinSky calling `rnd()` twice in sequence and getting two different stream values |

Other catalog entries labeled "per-pixel jitter" (Disco Ball, Psilocybin
Growth Formulae, Five Hole, Gedenghi, Unfolding Before You), Acid Flower,
Collapsing Sun, Uber Concert, g-life) are catalog auto-detection picking up
`rnd()` *anywhere* in the function, including pure setup use — those fields'
`rnd()` calls are all in §4's setup table and produce **no** per-pixel
spatial variation; the randomness is a single shared scalar, not a texture.
This distinction is not visible in the CallTree catalog table and was only
resolved by reading each field's per-pixel expression directly.

## 6. Proposed flo leaves

Mirroring `Port/Integration.md`'s `pipe.cell.rule.<name>` pattern, a
`pipe.field` (or `pipe.cell.field`) subtree:

```
field (on 0) {
    algo    (buffer, seg, x 0…23 = 0)        // field selector, see §... table above
    seed    (buffer, y 0…4294967295 = 1)     // per-pixel rnd() seed; editing triggers regen
    fader   (buffer, x 0…20000 = 10000)      // WinSky fader.v() domain; host divides /10000 -> fadeGain
}
```

Plus per-field `a[]` slots worth exposing as tunable leaves (visually
meaningful knobs, not incidental constants) — a conservative shortlist, not
all 15 a[]-using fields:

- **Poinsetta** `a0` (petal/spike count, WinSky default 32) — obvious
  "petal count" slider.
- **Uber Incognito** `a1` (WinSky default 16.8, quantization grid density)
  — "mosaic scale" slider.
- **6 Ft. Under** `a0` is a pure derived reciprocal (`1/0.7`) tied to the
  hardcoded `0.7` inside the field body itself — not independently
  meaningful without also exposing that `0.7`; skip unless the body constant
  is also parameterized.
- **Disco Ball** `a0` (segment count, `rnd(10)+15` → range 15..25) — expose
  as a slider with that same range instead of a fixed reroll-only random, so
  a user can dial "burst density" directly.
- **Gedenghi** `a1`/`a2` (ripple/kaleidoscope fold counts) — good "symmetry"
  knobs.

All other `a[]` uses are either fixed trig constants (Lens Flare) or
setup-random values whose *only* reasonable UI is "reroll" (i.e. bump
`seed`), not a direct slider — leave those as regen-only.

## 7. Divergence notes (every intentional deviation from WinSky, in one place)

### 7.1 Grid-aspect vs per-field `Aspect` argument
Every `Go*()` macro call takes an `Aspect` argument (e.g. `GoRT(R,T,0.25)`
for Ether Leak) that the catalog table surfaces as "Aspect=0.25" etc. Reading
`Field.cpp`'s `ForXY`/`Setup` macros directly (not just CallTree.md's
summary) shows this argument only assigns the otherwise-unused member
`this->aspect` — **it does not affect the `x` domain of the per-pixel loop**,
which is always `[-xya, xya]` where `xya = xs/ys` is the *grid's* aspect
ratio (`Field::init()`), fixed for all fields simultaneously. Since
DeepMuse's cell chain is a fixed 2048×2048 square, `xya == 1.0` for every
field regardless of its catalogued per-field `Aspect` value. This port
therefore ignores the per-field `Aspect` numbers entirely (they are cosmetic
metadata in the catalog, not live inputs) — confirmed by grep across
`Field.cpp`: `aspect` (the member) is never read anywhere after being
assigned.

### 7.2 `fade[]` LUT replaced with a direct linear formula
`Field::calcFade()` builds `fade[i] = min(255, (int)(i * fader.v()/10000.0))`
for `i` in 0..255 — a 256-entry table, but the *formula* it encodes is
strictly linear (`clamp(i*gain, 0, 255)`), not an arbitrary curve. Baking a
LUT buys nothing over evaluating the same clamp-multiply inline, and a LUT
would need its own texture/buffer binding for no behavioral gain. Ported as
`clamp(warpedSample * fadeGain, 0, 1)` directly in `fieldApplyKernel`,
mathematically identical (scale-invariant: `clamp(x*g,0,255)/255 ==
clamp((x/255)*g, 0,1)`).

### 7.3 Two WinSky buffers collapsed into one DeepMuse texture
WinSky's per-frame blend reads from two logically distinct sources: `buf
[bufi^1]` (the field's own previous-output feedback buffer) for the warped
term, and `main.pic.mix` (this frame's fresh camera+draw composite,
*unwarped*) for the incoming term. DeepMuse's existing `pipe.cell` chain
(used by every other `cell.rule.*.metal` rule) has no equivalent split — a
rule's single `inTex` (`pipe.cell.real`) already plays *both* roles across
frames, because `pipe.cell.real <- (draw.out, camera.out)` each frame while
`draw.out` is itself fed from the *previous* frame's `pipe.cell.out` via
`pipe.draw.in <- cell.out` (`Port/Integration.md` cross-reference table).
`fieldApplyKernel` follows that same established convention: `prevTex`
(bound to `pipe.cell.real`, matching every other cell rule's `texture(0)`
input) is read **twice** — once through `mapTex` (the decayed/warped term,
`val1`) and once directly at `gid` (the fresh term, `val2`) — rather than
introducing a third, field-specific texture binding that the rest of the
`pipe.cell` chain has no equivalent for. Net effect at the shader level is
identical to WinSky's two-buffer formula; the difference is purely about
which host-side texture feeds which read, and is forced by DeepMuse's
existing single-feedback-loop pipeline architecture rather than being an
arbitrary simplification.

### 7.4 Nearest nomodulo wrap, ported literally (not floor-based)
`Field::setFxy()` uses `(int)(...)  % xs` plus a single `+= xs` correction —
truncate-toward-zero, not `floor()`, and only ONE wrap correction (not a
general `((n % m) + m) % m`). This is preserved literally rather than
switched to a more robust floor-based wrap, since (a) "favor correctness"
here means bit-fidelity to source behavior, and (b) every one of the 24 live
field bodies keeps `fromX`/`fromY` within roughly `[-2,2]` (verified per-
field in §5/§4 — no unbounded terms), so a single correction is always
sufficient and no behavioral gap exists in practice. An `isfinite()` guard
was added as defense against the theoretical NaN/Inf case (which would be
undefined behavior in WinSky's own `(int)` cast) — inert for all 24 live
fields, present only as a robustness backstop.

### 7.5 `double` → `float`
WinSky's field math is entirely `double`. Apple GPUs (and Metal Shading
Language) have no compute-capable `double` type — every value in this port
is `float`. Expected, unavoidable, and immaterial at 2048-pixel grid scale
(`Port/Stubs.md` already documents `float`-only Metal math as the standing
convention for this whole port effort).

### 7.6 `rnd()` reseed model
See §5 header — hash-of-`(seed, algo, gid, slot)` replaces libc
`rand()`/`srand(time(NULL))`. Deterministic and reproducible given the same
`seed` (WinSky's wall-clock reseed is inherently non-reproducible run to
run), which is a strict improvement for testing/screenshots, not just a
necessary GPU-parallelism accommodation.

### 7.7 Per-channel application, not `.b`-only state packing
The `ave`/`zha`/etc. cell rules pack CA state into `.b` (primary) / `.g`
(inverse) / `.r`+`.a` (HiC counter) — a convention specific to those
automata, documented in `Port/Stubs.md`. WinSky's `Field` engine instead
operates on `Pix buf[2][FaceMax]`, independent image planes (`fixCount` of
them) that all share the *same* baked `fxy[]` warp table but blend
independently — i.e. fields warp a genuine multi-plane *image*, not a
single scalar automaton state. This port applies the identical warp +
blend formula to all 4 `half4` channels of the `bgra8Unorm` cell texture at
once (`fieldApplyKernel`'s `half4` arithmetic), the natural generalization
of WinSky's per-plane loop — **not** the `ave`/`zha` `.b`/.g/.r+.a packing,
which does not apply to this subsystem.

### 7.8 Out-of-range `algo`
WinSky's `algo.v()` is a UI-bounded `BudInt`; an out-of-range field index
cannot occur in the real engine (the sequential `Test()` counter simply
never matches and `calcMap()` falls through with no warp computed — a latent
no-op, not a defined fallback). This port's `switch` uses `default:` to fall
back to case 23 (Lens Flare) for any `algo >= 24`, purely so the kernel has
defined behavior for a malformed uniform upload — not a WinSky behavior.
