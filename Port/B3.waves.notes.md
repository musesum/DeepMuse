## 1. Kernel shape: SCATTER, not GATHER

Every existing `cell.rule.*.metal` kernel (`Integration.md`) dispatches one
thread per **pixel** over the full 2048×2048 grid. `waveKernel` dispatches one
thread per **point**: a 1D grid of `uniforms.num` threads. Each thread decodes
its `gid` into an (instance, step) pair of the selected wave shape, evaluates
that shape's `setup`/`frame`/`pixel` math for exactly that one `(id, s)`, and
scatter-writes the resulting 1–20 points into the shared cell texture.

### Thread → (instance, step) decomposition (identical for all 68 shapes)

```
STEPS    = algoSteps(algo)                    // per-shape constant, see §4
stepIdx  = gid % STEPS
instIdx  = gid / STEPS
s        = (STEPS>1) ? stepIdx/(STEPS-1) : 0  // matches source's sint/steps
id       = float(instIdx)
numF     = max(1, floor(uniforms.num / STEPS))
```

Host controls live instance count purely through `uniforms.num`: setting
`num == STEPS` reproduces the source's single-instance behavior exactly (all
47 waveshort shapes bar 3, and roughly half of PartiShort); setting
`num == STEPS * K` renders `K` instances. No per-shape instance count is
baked into the kernel — this sidesteps every shape whose source instance
count is itself an `rnd()` expression (`CircWarp`, `Miris_Ball`, `Pop_Circles`,
`Snakes`, `Juggler`, `Orbiting_Rods_N_Sticks`, `Protozoan_Lovers`): those
become host/flo-adjustable live parameters instead of a fixed roll.

## 2. WaveUniforms — buffer(0), exact byte layout

Mirror this struct exactly in Swift (`MTLBuffer`, 44 bytes, no padding,
all fields `Float32`):

| Field | Offset | Type | Meaning |
|---|---|---|---|
| `algo` | 0 | float | shape select, `int(algo)` clamped 0..67 — see §4 table |
| `t` | 4 | float | elapsed seconds (source `t`) |
| `num` | 8 | float | total 1D dispatch thread count this frame (= points to evaluate) |
| `ux` | 12 | float | UI slider X (source `ux`) |
| `uy` | 16 | float | UI slider Y (source `uy`) |
| `ur` | 20 | float | UI slider R (source `ur`) |
| `ua` | 24 | float | UI slider A (source `ua`) — **unreachable**: grepped both expanded files, `ua` appears only in the function signature/header comment, never inside any of the 68 live shape bodies. Kept in the uniform for signature parity with the source's `User` struct and forward-compatibility (PartiShort/waveshort archive shapes not in scope here do use it) |
| `seed` | 28 | float | rnd() reseed key — host must bump this whenever `algo` changes (reroll-on-select) |
| `selectT` | 32 | float | `t` value at the last `algo` change — host must set this in the SAME event as bumping `seed`. Powers the `a[0]=t; …(t-a[0])…` "time since selection" idiom (§5) |
| `magCount` | 36 | float | valid element count in the `mag` buffer; 0 = silent/no tap |
| `fftCount` | 40 | float | valid element count in the `fft` buffer; 0 = silent/no tap |

## 5. Divergences (documented, binding per task brief)

1. **In-place `read_write` single texture, not the gather dual-texture
   convention.** `Integration.md`'s `texture(0)=read input / texture(1)=write
   output` pattern assumes every dispatch repaints the whole frame. A scatter
   kernel only touches the handful of pixels it draws this call; if bound
   with a fresh/blank `outTex` the way `CellNode.computeShader` currently
   wires cell rules, everywhere else in the 2048×2048 grid would go blank
   every frame. `waveKernel` instead reads-modifies-writes the SAME texture
   the rest of the pipeline already holds (`texture(0)`, `access::read_write`).
   **Host integration implication (not implemented here — no existing files
   were edited per the task brief):** wiring this kernel into `CellNode`
   requires either a new dispatch path that binds `pipe.cell.out` at
   `texture(0)` in place (not `fake`/`real`/`out` ping-pong), or a dedicated
   `WaveNode` alongside `CellNode` that does a 1D `dispatchThreads` instead of
   the fixed 16×16-threadgroup full-frame dispatch in
   `Mu/MuVision/.../Pipeline/ComputeNode.swift:40-47`.

   > **Correction, 2026-07-11 (implemented):** a dedicated `WaveNode`
   > (`Mu/MuVision/Sources/MuVision/Pipeline/WaveNode.swift`) was built, as
   > the second alternative sketched above — but two details in this
   > divergence turned out wrong once actually run under
   > `MTL_DEBUG_LAYER=1` on simulator:
   > - **Single `access::read_write` texture argument is invalid** for a
   >   `bgra8Unorm` texture (`validateComputeFunctionArguments` assertion).
   >   `waveKernel`'s texture argument was split into
   >   `access::read` `cellIn` at `texture(0)` and `access::write` `cellOut`
   >   at `texture(1)`; `wsWritePoint`'s signature changed from one
   >   `read_write` texture to `(texIn, texOut)`. `WaveNode` binds
   >   `pipe.cell.out` to **both** slots, so the net effect — one physical
   >   texture, read-then-write per thread, no ping-pong — is exactly what
   >   this divergence describes; only the Metal-side argument shape changed.
   > - **`dispatchThreads` (non-uniform threadgroups) is unsupported on the
   >   simulator feature set**, contrary to the "1D `dispatchThreads`" phrase
   >   above. `WaveNode.computeShader` uses uniform
   >   `encoder.dispatchThreadgroups` with a round-up group count
   >   (`(num + tgWidth - 1) / tgWidth`); `waveKernel` already guards
   >   `gid >= num`, so the round-up's extra padding threads are inert.
   >   `CellNode`'s fixed 16×16 full-frame dispatch (`ComputeNode.swift:
   >   40-47`) is unaffected — `WaveNode` has its own dispatch call, it does
   >   not go through `ComputeNode`'s.
2. **Overwrite races are accepted (last-write-wins).** Multiple threads can
   target the same output pixel (same shape drawing overlapping points, or
   two different points from different steps landing on the same texel after
   quantization). This matches the *sequential overdraw* semantics of the
   source's single-threaded per-frame rasterizer — the source also lets a
   later `Draw::circle()`/`Draw::line()` call overwrite an earlier one — so
   the only real change is that draw order across threads is now
   GPU-unspecified rather than the source's guaranteed per-step order. No
   correctness issue, just a documented nondeterminism in *which* value wins
   when two points coincide on the same frame.
3. **`connect==1` polylines degrade to independent dot scatter.** The
   source's `Draw()` macro can either plot `xyiMax+1` independent dots
   (`connect==0`) or connect them into a polyline (`connect==1`). A per-thread
   scatter kernel has no access to a neighboring thread's points to draw a
   line segment between, so every shape — regardless of source `connect`
   value — writes its `xyiMax+1` points as independent single-pixel dots.
   Visually this turns continuous strokes (e.g. `Dancing_String`, `Spectagon`,
   `Tension_II`) into point clouds; the point *positions* are otherwise exact.
4. **`draw()`'s `width` argument is dropped.** No stroke-thickness/point-size
   rasterization is implemented (would require a small splat kernel or
   geometry expansion, out of scope for a first-pass scatter port). Shapes
   whose `width` argument was their only "reactive" element (e.g.
   `SM_Spectometer`'s dot thickness, `Tosser`'s `mag(s)*ux*20`) have that term
   computed-then-discarded in-kernel (marked `(void)` at the call site) so the
   port stays traceable to source rather than silently dropping the line.
5. **`rnd(n)` is a deterministic hash, not a libc stream.** Replaced by
   `wsRnd(instIdx, algo, uniforms.seed, callSiteCounter, reseedFold, range)` —
   stable for a given (instance, algo, seed), reproducing the source's
   "rolled once at selection, held for the shape's lifetime" behavior without
   any persistent buffer. Reroll-on-select is just bumping `uniforms.seed`.
   `seed(x)` (source: reseeds the global libc RNG, used as `WaveVars`-style
   chaining) folds `x` into the same per-thread hash chain instead
   (`wsSeed`); its *return value* (== `x`) is source-unused everywhere in
   these 68 shapes except as a chaining side effect, confirmed by grep.
6. **`a[]`/`b[]`/`c[]` registers are zero-initialized per thread per frame,
   not persistent.** In the source these are member arrays that survive
   across frames (and, within `setup`, across the whole shape selection).
   Because every SCATTER thread is independent and stateless, any source
   idiom that reads a register **before** it is written *this pass* — reading
   whatever was left by a previous frame's pass — reads `0` here instead.
   Two concrete cases in scope (both already flagged as known engine quirks
   in `CallTree.md` §6 point 8, not something the port introduced):
   - **`Critters`** reads `c[1]` before assigning it. Reordered in the port
     (assign first) rather than reading always-zero garbage — see inline
     `NOTE(port)` at case 17.
   - **`SpinIt`** reads `c[0]` before assigning it. Same fix, same rationale
     — see inline `NOTE(port)` at case 33.
   `Hourglass`'s documented interleaved `c[5]` reuse (CallTree §6.3) turned
   out to be moot for this port: the second `c[5]` value only ever fed
   `draw()`'s `width` argument, which divergence 4 already drops.
7. **`Orbiting_Stars`' three-body gravity accumulator cannot be stateless.**
   Its `b[]` block is a genuine frame-to-frame position integrator (`b[2] =
   b[1]*(b[2]+b[17]+b[19])+b[0]*a[23]`, etc.) — not a same-pass ordering
   quirk like the two cases above, but real persistent simulation state, which
   contradicts this file's "waves recompute every frame from `t`" framing for
   every *other* shape. A stateless SCATTER thread cannot carry that forward.
   The port always evaluates the source's `b0==1` ("just selected") branch,
   which is well-defined and self-contained (all terms derive directly from
   the `a[]` initial-condition constants). Net effect: a stable, audio-modulated
   three-point rosette instead of genuine chaotic orbital drift. True fidelity
   would need a persistent per-instance state buffer and a second kernel pass
   — future work, out of scope for this port.
8. **`a[0]=t; …(t-a[0])…` "selection anchor" idiom → `uniforms.selectT`.**
   Recomputing `setup` fresh every thread/frame (divergence 6) means a naive
   `a[0]=t` always reads the *current* frame's `t`, collapsing `t-a[0]` to
   always 0 and breaking every shape that uses "elapsed time since this shape
   was selected" as an animation driver. Those specific shapes use
   `uniforms.selectT` (which the host sets to `t` only on an `algo` change,
   the same event that should bump `uniforms.seed`) in place of a fresh `t`
   read for that one anchor. Affected shapes (verified by grep — the anchor
   is load-bearing, i.e. actually reaches the drawn `x[]`/`y[]`, not dead):
   `Cycling_Dots` (6), `Pollock_Spectagon` (11), `Sparkling_Table_Water` (47),
   `Solala` (48), `Pollock_Dots` (57), `Pop_Circles` (58), `Protozoan_Lovers`
   (60), `Snakes` (61). `Orbiting_Stars` (42) uses this pattern too but is
   handled separately per divergence 7 (forced always into the `b0==1`
   branch, so its `a[0]` anchor is moot). `CircWarp`'s `a[0]=t` and `Colliders`'
   `a[1]=t` are dead in source (never read downstream) and were dropped.
9. **`sampleSteps()`/`sampleSlots()`/`fftSlots()`/`fftSteps()` baked to a
   representative constant.** These are structural buffer-size accessors in
   the source (`WaveSky::samPerBuf`/`fftPerBuf`), not live signal, and no
   destination equivalent exists yet (`Stubs.md` audio-reactive gap table).
   Baked to `kSampleSteps = 1024.0` everywhere (STEPS-only uses like
   `Father_and_Daughters`/`Tension_II`/`Walls_of_Sound` bake their literal
   directly into `algoSteps()` instead, see §4). Revisit when a real
   `AmplitudeTap`/`FFTTap` buffer size is known (§7).
10. **`timeEnd()` → `uniforms.selectT + 1200.0`.** Matches the source's
    default auto-advance duration (`Waveshapes.cpp`, `endtime = startime +
    1200`); only `Solala` (48) and `Tosser` (63) reference it, neither has a
    `Duration(...)` override in this shortlist.
11. **`aspect` (source per-shape `0`/`1` flag) is a no-op.** The destination
    canvas is always the square 2048×2048 cell texture, so there is no
    non-square aspect ratio for it to correct. Dropped rather than ported.
12. **Coordinate convention.** Source normalized coordinates are mapped
    `u = x*0.5+0.5`, `v = 0.5 - y*0.5` (y-up NDC → top-left-origin texture row
    order) in `wsWritePoint`. This is an assumption, not verified against a
    running build (no device/simulator target was exercised as part of this
    task) — flip `v` here first if a device test shows the wave shapes
    rendering upside down.
13. **`ua` (4th UI slider) is unreachable from all 68 live shapes** — grepped
    both `waveshort.expanded.cpp` and `PartiShort.expanded.cpp`, confirmed
    against the WinSky source read-only. Not a bug; `ua` is kept in
    `WaveUniforms` for signature parity and forward-compatibility only. This
    is the sole remaining compiler warning (`-Wunused-variable`).
14. **`Tosser`'s frame-phase `b[8]=mag(s)*ux*20`** reads `s` before the
    source's per-step loop defines it (a `WaveShape`-member stale-`s` read,
    same *class* of hazard as divergence 6 but in a variable the source
    doesn't even declare per-frame). This port's only sensible stand-in is
    the evaluating thread's own `s` (see inline comment at case 63); the
    result only ever fed `width` anyway (divergence 4), so it is computed and
    discarded.

## 6. Audio shim requirements (Wave C)

Per `Stubs.md`'s existing gap table, `MuAudio` has no amplitude/FFT tap today
(`AudioEngine()` is only ever instantiated for a test oscillator). This
kernel is written to **degrade gracefully to silence** with zero-length
buffers (`magCount`/`fftCount` == 0 ⇒ `wsMag`/`wsFft` return `0.0`
unconditionally) so it can ship and compile before that gap closes — but most
of the 68 shapes are visually inert without real audio (`mag`/`fft` drive
radius/amplitude/color terms in the large majority of cases).

Suggested shim (mirrors `Stubs.md` gap items 1–2, AudioKit already linked):
- `AmplitudeTap` on `MuAudio.audioEngine`'s output node → ring-buffer of N
  time-domain samples → upload to `buffer(1)` each frame, set
  `uniforms.magCount = N`.
- `FFTTap` (or a `vDSP_DFT` pass) on the same tap point → M magnitude bins →
  upload to `buffer(2)`, set `uniforms.fftCount = M`.
- Both taps are per-frame CPU→GPU uploads (small, N/M in the hundreds), not
  a new Metal buffer-binding path — `CellNode.computeShader` already needs
  extending to bind buffers beyond index 0 for this kernel regardless (see
  `Stubs.md` gap item 5), so land this alongside that work.
- `beat()` stays hardcoded `1.0` (matches source's own `WaveSky::beat()`
  stub) — no destination beat-detection shim is proposed here; that's a
  separate, unrelated gap (`Stubs.md` gap item 3).

## 7. Proposed flo leaves

Following the `pipe.cell.rule.<name> (on 0) { version(buffer_0, …) }`
convention in `Integration.md` §"Pipeline flo leaf", scaled to this kernel's
uniform count. Not wired into any existing `.flo.h` file (no existing files
were edited per the task brief) — proposed shape only:

```
wave (on 0) {
    algo   (buffer, x 0…67 : 0)          // shape select, see §4 table
    num    (buffer, x 1…4096 : 100)      // dispatch thread count == points/frame;
                                          // set to STEPS*instanceCount for multi-instance shapes
    ux     (buffer, x -1…1 = 0)          // WinSky WaveshapeUserX default/range
    uy     (buffer, x -1…1 = 0)          // WaveshapeUserY
    ur     (buffer, x -1…1 = 0)          // WaveshapeUserR
    ua     (buffer, x -1…1 = 0)          // WaveshapeUserA (see divergence 13 -- currently inert)
    seed   (buffer, x 0…1e6 : 0)         // bump on algo change to reroll rnd()-derived constants
}
```

Notes on ranges:
- `algo` 0…67 matches this port's dispatch order exactly (§4); WinSky's own
  `ScreenWaveshapeAlgo` tree leaf has no declared range in the reviewed
  source (`WaveShapes::init()` just hardwires `algo.set(1)` at boot) so 0…67
  is this port's own convention, not a transcription.
- `num` default 100 mirrors the median STEPS value across the 68 shapes; the
  1…4096 range comfortably covers the largest single-instance case
  (`Thunderation`, STEPS=1024) with headroom for a few dozen instances on the
  smallest-STEPS multi-instance shapes (`Colliders`/`Orbiting_Rods_N_Sticks`/
  `Juggler`, STEPS=2).
- `ux/uy/ur/ua` range `-1…1` matches `WaveShapes::userX/Y/R/A` being plain
  `BudInt` slider leaves in the source with no declared asymmetric range
  found in the reviewed portion of `tree_demo.sky`; treat as provisional.
- `t`/`selectT` are **not** flo leaves — `t` is the existing global time
  uniform gap (`Stubs.md` gap item 5, `CellNode.frame`/wall clock, not yet
  bound to any buffer); `selectT` must be host-computed (Swift-side) as "the
  `t` value read the frame `algo` last changed," not something a flo leaf can
  express on its own. Whatever wires `t` into this kernel must also latch
  `selectT` in the same code path that detects an `algo` change (and should
  bump `seed` there too — see divergence 5/8).
- `magCount`/`fftCount` are derived host-side from the real tap buffer
  lengths (§6), not user-facing flo leaves.

### 2026-07-11 correction: shipped as `uxyn`, not separate `ux`/`uy`/`num` leaves

This section's proposal (separate `algo`/`num`/`ux`/`uy`/`ur`/`ua`/`seed`
leaves) was wired into `pipe.flo.h`, but `num`, `ux`, and `uy` were merged
into one `xyz`-typed leaf, `uxyn`, before landing — driven by the MuMenu
homogeneity constraint documented in `Integration.md`'s 2026-07-11 section
(a menu branch can't mix value exprs and children, and `xyz` composite

`WaveUniforms` Metal struct in §2 above is untouched: `ux`, `uy`, `num`
remain three separate `float` fields at their documented offsets 8/12/16;

uniform slots when building the buffer(0) array. A `version` leaf (buffer,
