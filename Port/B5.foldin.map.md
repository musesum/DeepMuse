## 0. How the template worked (input/map_cc.cpp, input/PenThread.cpp)

- Every printed zone = one `Place` (`map_cc.cpp:95-138`) hit-tested by pen x/y
  (`Map::setPlace` `:150-172`); a hit posts `<Zone>New` plus optional keys.
- **Two maps per zone.** `MapHi` fires when the pen's rocker switch is in the
  upper position (`pkButtons & ButtonHi`, `PenThread.cpp:382`), `MapLo` in the
  lower (`ButtonLo`, `:383`). Convention in `tree_demo.sky`: Hi = **fake** layer,
  Lo = **real** layer (`shift.fake.x << MapHiBoxNeHorizX`, `shift.real.x << MapLoBoxNeHorizX`, `:59-100`).
- `DispatchBox` (`input/DispatchBox.h`) = a second modal gate by quadrant
  (`DBoxPoly/View/Cam/Nw/Se/Ne/Sw/Nn/Ss/Ee/Ww`); palette zones only act when
  `dboxHi.now==DBoxSw` (`bind_cc.sky:441-465`).
- Zone → feature legend (from the PNG + `map_cc.cpp:233-660`):

| template area | zone names | drove |
|---|---|---|
| center dial, 8 outer + 12 inner swatches | `MapHiPalOne..Twelve`, `MapLoInnerOne..Ten`, `MuseSwatch` | palette recall (Hi), palette capture (Lo), add ramp (inner) |
| 8 white ovals around the dial | `DispatchBox*` corners | quadrant context: Poly / View / Cam / NW / NE / SW / SE |
| long grey bars N/S of the dial | `RenderForeBar`, `RenderBackBar`, `BoxNeHoriz/Vert`, `BoxSeHoriz/Vert` | eye z, near-distance, real/fake xy shift, palette inc / xfade |
| right column: 4 hearts, 4 triangles, 4 cubes, 4 vertical bars | `Beat{One..Four}{Rec,Play,Stop,Amp}` (Hi and Lo sets) | four-beat transport + per-beat LFO amplitude |
| right column: `½ 1 ×2`, `1‥8` | `MapHiBeatBar` (+ KeySpace) | bar subdivision / beat count |
| left column: 4×3 photo grid, L F R B, arrows | `MapHiFace*` (24 faces), `Slide{One,Hori,Vert,Single,Multi}` | polyhedron face picker, photo-strip orientation |
| bottom: black/white lozenges, drops | `KeyColor` (Hi/Lo), `KeyRange` | luma black / luma white / luma merge width |
| diamond pads left/right | `RenderMove*`, joystick | camera move, rotate |

Layout clues Dev asked for: beat = a 4-wide column of homogeneous rows
(one row per control kind, one column per beat); navigation (diamond pads,
arrows) sits apart from the XY value bars. The two-position rocker is the
precedent for "one pad, two layers" = today's dual-thumb `xyzw` pad.

## 1. Plato polyhedra — spring relaxation, vertex vs face normals

**WinSky.** `render/Polyhedra.cpp` builders (`buildIcosa`, `buildTetraCube`,
`buildCubeOct`, `buildOctCube`, `buildCubeDodec`, `buildDodecahedron`,
`buildDodecIcosa`), dispatched `render/Render.cpp:554-565`. Springs:
`Shape::calcVelocity` `render/Shape.cpp:337-407` — each `Vertex{p,h,v}` pulled
to home `h` by `k1 = 0.005` and to edge neighbours by `k2 = 0.6`; per frame
(`Render.cpp:186-194`): `calcVelocity; addNormal; if pressable {filterVelocity; addVelocity}; calcNormals`.
Normals: `Shape::calcNormals` `:142-210`, `faceBlend` selects per-vertex
(blended) vs per-face; set from `blend` BudInt (`Render.cpp:637-638`).
Controls (`tree_demo.sky:1338-1345`): `depth 0..7000=2000`, `icosa 0<>1`,
`blend 0<>1=1`, `pressable 0<>1=1`, `pressure 0<>1=0 << JoyButtonA`.

**DeepMuse today.** `MuPlato/PlatoConstants.swift:6-42` = fixed vertex table
(Z, T0-3, C0-3, O0-5, D0-B, I0-B + phase vertices); morph is a shader lerp of
`pos0→pos1`, `norm0→norm1` by `range01` (`PlatoVertex.swift:10-11`,
`PlatoNode.swift:11-52`). No `spring`/`relax` symbol anywhere. `norm0/norm1`
are computed per FACE (`PhaseTriangles+update.swift` takes the cross product of
each triangle and stamps it on the three corners); there is no per-vertex
(averaged) path. (Corrected 2026-09-09: the first draft had this inverted.)

**Gap.** (a) a CPU or compute-kernel relaxation pass over the vertex buffer
(home + edge springs, two constants, a `pressable` gate); (b) a `blend` switch
between per-face (today) and per-vertex normals (average of the face normals
meeting at a position; the vertex table already duplicates corners per face).

**MuMenu.** No new leaf type. `plato.flo.h` additions in Dev's style:
```
spring ('vertex relaxation', xyz,
        x 0…0.05=0.005, 'k1 home spring',
        y 0…1=0.6,      'k2 edge spring',
        z 0_1=0,        'pressable (0 = rigid)',
        svg "icon.plato.phase")
normal ('shade per face (off) or per vertex (on)', tog, x 0, sym "triangle")
```
Pipeline edits: `PlatoNode` binds `spring˚`/`normal˚`; relaxation step before
the vertex-buffer upload (or a compute kernel on the same buffer). Vertex
count is small (≤ icosa subdivided by `phase.y 0…6`), CPU is fine at 60 fps.

## 5. Real / false color layers, luma-key mix, two grab points

**WinSky.** `win/Win.cpp:481-533` `Win::setFade`:
```

w = ratio(-m, mxi, lumaWhite)
b = ratio(0, mxi+m, lumaBlack)
fades[real] = fadeReal; fades[fake] = fadeFake

```

`Win::setBmp`/`rePlane` (`:604-630`). Tree (`tree_demo.sky:1413-1426`):
`realfake 0..100=50`, `fade.real/fake 0..1000`, `luma.size 0..12700=700 << MapHiKeyRangeX`,
`luma.black 0..25600=0 << MapHiKeyColorX`, `luma.white 0..25600=25600 << MapLoKeyColorX`,
plus LFO-driven twins `osize/oblack/owhite << LfoFive/Six/Seven`.

points" were the two rocker positions on the same `KeyColor` zone: Hi = black
cutoff, Lo = white cutoff. Layers: `fake` = palette-mapped automaton, `real` =
photo/camera RGB; `pic/Mix.cpp` `MixOp {zero,mov,add,sub,and,or,xor}` on
`plane/bits` is a different, per-rule bitplane mixer (superseded, unported by
decision).

**DeepMuse today.** `pipe.cell.fake (<- draw.out)`, `pipe.cell.real (<- (draw.out, camera.out))`
(`pipe.flo.h:14-15`) — the split exists at the automaton input.

`pairMix` = doubled-occupant decode. `camix.mixcam` = linear camera crossfade.
No `luma` symbol in MuVision/MuSky. `sky.color.xfade` fades pal0↔pal1.

**Gap.** A luma-key stage: `key(real, fake, black, white, merge)` → per pixel
`t = smoothstep(black − merge, white + merge, luma(real))`, mix. Cleanest seat:
extend the `camix` kernel (it already has both textures in hand) with a
`luma (buffer, x black, y white, z merge)` uniform; `mixcam` stays the manual
crossfade (= WinSky `realfake`).

**MuMenu.** Dev's "could be a xyzw control" = the existing dual-thumb pad
(`LeafXyzwVm`, runways `[.runX,.runY,.runZ,.runW,.runXY,.runWZ]`,
`BranchVm.swift:102`): thumb 1 (x,y) = real cutoff pair, thumb 2 (w,z) = false

     x 0…1=0,   'real black',
     y 0…1=1,   'real white',

## 9. H / V / Z stack in MuMenu syntax

Today: branch-level ints only — `columns N` (`plato.flo.h:2`, `cell.flo.h:1`),
read by `BranchVm.swift:66`, rendered by `LazyVGrid` (`BranchView.swift:102`);
orientation comes from the corner (`MenuType` `MenuOp.swift:28-183`,
`cornerAxis` `:80-92`), and the vertical override set is a literal
(`BranchView.swift:177`). Constraint on file: branches carry no value exprs
(homogeneous-branch rule), so a stack marker must be a branch attribute like
`columns`, not a leaf expr. `PanelVm.init` (`PanelVm.swift:19-37`) sizes a
multi-leaf branch as `.node` — a stack of mixed leaves needs per-child sizing.

Proposal (Dev's words: H, V, Z stack):
```
beat (vstack, sym "metronome") {          // rows
    transport (hstack) { rec (tap) play (tap) stop (tap) sync (tap) }
    amps      (hstack) { one (val) two (val) three (val) four (val) }
    lfos      (hstack) { one (lfo) two (lfo) three (lfo) four (lfo) }
}
palette (zstack) { index (xy) strip (pal) }   // z = overlay, back to front
```
- `hstack` / `vstack` / `zstack` = branch attributes beside `columns`; a branch
  with one of them lays its children out as SwiftUI `HStack`/`VStack`/`ZStack`
  instead of `Body_`/`Grid`; nested stacks compose (rows of columns).
- Sizing: `PanelVm` sums child `aspectSz` along the stack axis, max across;
  `zstack` = max of both.
- `columns N` stays as the shorthand for `vstack{hstack×N}` of like children.
- Touch: `zstack` children need hit priority top-first; `LeafRunways.activePad`
  (dual-thumb pad) is the precedent for choosing the receiver.
- The RSI strategy already flags `setAspectFromType` as the single control-shape
  function (`project_muflo_rsi`); stacks generalize it rather than adding literals.
