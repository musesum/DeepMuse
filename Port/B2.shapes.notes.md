Compile validation: `xcrun -sdk iphoneos metal -c <file> -o <out>.air`, all
four exit 0, zero warnings. Note: this Metal SDK has no free `hypot`
overload — `_hypot(xx,yy)` in source is ported as
`metal::length(float2(xx,yy))` (exact equivalent, Euclidean norm builtin) in
spiral/circle/floral; documented in each kernel's header comment.

All four shapes are **gather-safe procedural fields** per `Port/CallTree.md`
§2/§4: pure function of `(x,y)` distance/angle from grid center plus a
self-only `hc` feedback term through the `NextR` macro convention — **zero
neighbor reads**, so none of these four kernels need the `n/s/e/w[/nw/ne/se/sw]`
boundary-index macro block that `cell.rule.fred.metal`/`cell.rule.ave.metal`
use. Each kernel reads only `inTex.read(gid)` (self) for the `HiC` high-word
carry, matching the destination convention (`.b`=primary, `.g`=255−primary,
`(.a<<8)+.r`=HiC), reproduced literally from the source `NextR` macro
(`pixel/Rule.cpp:92-95`: `r1`→`.b`, `r2=255-r1`→`.g`, `r3=hc+(r1&3)`→HiC).

## Required CellNode binding extension (buffer(1) — CRITICAL, unbound today)

`Port/Integration.md` and `Port/Stubs.md` both state the pipeline binds
**only buffer(0)** today (`Mu/MuVision/.../Pipeline/CellNode.swift:52-68`
sets `version˚` at index 0 and the two textures; nothing else).
`cell.rule.melt.metal` already ships a `constant float& bits [[buffer(1)]]`
that is silently unbound (`Port/Stubs.md` gap #6) — that is a **known,
already-tolerated hazard class** in this codebase, not new here, but three
of the four kernels below (`spiral`, `circle`, `floral`) add MORE such
declared-but-unbound `buffer(1)` structs. **Until `CellNode.computeShader`
is extended to bind a second buffer, all three will read undefined/garbage
memory at buffer index 1 at runtime** — do not enable these rules in the
live menu/pipe flo trees before the binding extension lands.

### Struct layouts (exact — Swift-side mirror structs MUST match field order and size)

```metal
// Metal/cell.rule.spiral.metal
struct SpiralUniforms {
    float cone1On;         // offset  0
    float cone1Scale;      // offset  4
    float cone1Strength;   // offset  8
    float circleOn;        // offset 12
    float circleRays;      // offset 16
};
// sizeof == 20 bytes (5 x float32, no padding — all-float struct, 4-byte natural alignment)
```

```metal
// Metal/cell.rule.circle.metal
struct CircleUniforms {
    float cone1On;         // offset  0
    float cone1Scale;      // offset  4
    float cone1Strength;   // offset  8
    float cone2On;         // offset 12
    float cone2Scale;      // offset 16
    float cone2Strength;   // offset 20
};
// sizeof == 24 bytes (6 x float32, no padding)
```

```metal
// Metal/cell.rule.floral.metal
struct FloralUniforms {
    float randomOn;        // offset  0   — inert in-kernel, host reroll trigger only
    float cone1On;         // offset  4
    float cone1Scale;      // offset  8
    float cone1Strength;   // offset 12
    float cone2On;         // offset 16
    float cone2Scale;      // offset 20
    float cone2Strength;   // offset 24
    float circleOn;        // offset 28
    float circleRays;      // offset 32
    float columnOn;        // offset 36
    float columnNum;       // offset 40
    float columnRays;      // offset 44  — unread by Rule::floral, kept for layout parity
    float columnStrength;  // offset 48
    float petal1On;        // offset 52
    float petal1Num;       // offset 56
    float petal1Spiralz;   // offset 60
    float petal1Petalz;    // offset 64
    float petal1Strength;  // offset 68
    float petal2On;        // offset 72
    float petal2Num;       // offset 76
    float petal2Spiralz;   // offset 80
    float petal2Petalz;    // offset 84
    float petal2Strength;  // offset 88
};
// sizeof == 92 bytes (23 x float32, no padding)
```

All three structs are **homogeneous `float`-only** by design specifically so
byte layout is trivially predictable (4-byte natural alignment, zero
inter-field padding on both Metal and Swift/`MemoryLayout`) — a Swift struct
declared with `Float` fields in the SAME order reproduces this layout exactly
via `MemoryLayout<T>.size`/`.stride`, no manual padding needed.

## Floral reroll host-side design note

Source behavior (`pixel/Rule.cpp:525-526`, `pixel/Floral.cpp:36-65`):
every time `Rule::floral` runs and `flor.randomOn.v()>0`, it calls
`flor.random()` FIRST, which re-rolls all ~20 other `Floral` `BudInt`
members (cone1/cone2/circle/column/petal1/petal2 — every field in
`FloralUniforms` except `randomOn` itself) to a fresh random value inside
each field's own tree-declared range, in place, on the CPU — THEN evaluates
the per-pixel field using those freshly-rolled values for every cell in that
frame. This is a genuine once-per-frame stateful mutation, not a per-pixel
computation, and cannot be expressed inside `floralKernel` (a compute kernel
cannot rewrite the `constant` buffer that parameterizes its own dispatch).

**Interim / current kernel behavior (implemented above):** `floralKernel`
ignores `randomOn` entirely and renders deterministically from whatever
`FloralUniforms` values it is handed for that dispatch. This is correct and
safe as long as nothing upstream claims frame-to-frame randomization is
happening — it simply will not, until the host-side reroll below is built.

**Proposed host-side design (not implemented — Wave-C scope):**

1. **Where it runs:** once per frame, on the CPU/host, BEFORE `CellNode`
   encodes `floralKernel`'s dispatch for that frame — i.e. as either (a) a
   `flo` leaf write triggered from the same place `CellNode` currently reads
   `version˚` (`CellNode.swift:53-54`), or (b) a tiny separate MuVision
   "reroll" pass that runs on the CPU and rewrites the flo leaves that back
   `FloralUniforms`' 22 non-`randomOn` fields, each within its OWN
   already-declared range (same ranges as the parameter table above — reroll
   must respect per-field min/max, not roll globally).
2. **Trigger condition:** mirror the source exactly — reroll happens once
   per frame IF AND ONLY IF the `randomOn` leaf (`pipe.cell.rule.floral.randomOn`)
   is currently on. `randomOn` itself is never rerolled (matches
   `Floral::random()`, which reads `randomOn.v()` in the CALLER — `Rule::floral`
   — not inside `random()` itself; `random()` only touches the other 20
   members, confirmed by `pixel/Floral.cpp:36-65`).
3. **Where NOT to put it:** not inside `floralKernel` (buffer(1) is
   `constant`, read-only from the kernel's perspective by Metal API
   contract — CellNode uploads it fresh via `setBytes` each encode, so the
   kernel has no mechanism to write back into it even in principle without a
   second read-write buffer pass, which is unwarranted complexity for what
   is fundamentally a CPU-side parameter randomization, not a GPU
   computation).
4. **Dead-code note carried forward:** `Rule::flora` (Rule.cpp:601-679, no
   caller anywhere in source per `Port/CallTree.md`) is NOT a template to
   follow for this reroll — it always randomizes every field including
   on/off flags every call, which is a DIFFERENT (more aggressive) behavior
   than the live `Rule::floral`'s conditional, `randomOn`-gated reroll. If
   an "always maximally randomized" floral variant is wanted later, it is a
   product decision to permanently force `randomOn` true, not a separate
   reroll algorithm.

### 2026-07-11 correction: `randomOn` retired, `FloralUniforms` now 22 floats

> Refactor.h (2026-07-11): the "Required CellNode binding extension" and
> "Floral reroll host-side design note" sections above describe a
> `randomOn`-gated host-side reroll pass. That pass was never built — a
> deliberate product decision, not an oversight. `randomOn` was removed
> instead: `FloralUniforms` (§"Struct layouts") drops its leading
> `randomOn` field and is now 22 floats / 88 bytes (was 23 floats / 92
> bytes); the live `Deep/Muse/Metal/cell.rule.floral.metal` struct comment
> reads "reroll-trigger field removed 2026-07-11 (Refactor.h)".
> `floralKernel` renders deterministically from whatever uniforms it is
> handed each frame — exactly the "interim" behavior this document called
> out as correct-for-now (§"Floral reroll host-side design note") — and
> that is now the permanent behavior, not an interim one.
>
> The "five edit sites" cross-reference above was completed differently
> than proposed: no `buffer_1`-tagged per-scalar leaves and no per-shape
> on-flag leaves landed. Instead `more.flo.h`'s `mic.shapes` block binds
> five composite `xyzw`/`xyz`/`seg` leaves (`cone`/`petal`/`spiral`/
> `column`/`circle`) shared across all three parameterized kernels, and
> `ShapeNode` (`Mu/MuVision/Sources/MuVision/Pipeline/ShapeNode.swift`)
> assembles each kernel's buffer(1) array from those components per frame,
> deriving on-flags as `component > 0` rather than reading a separate
> on-flag leaf. Full mapping, the new `.xyzw` MuMenu control, and
> verification: `Port/Integration.md`'s "2026-07-11 Refactor.h — xyzw
> consolidation" section.
